# Lab-guide framework

Loaded on demand when files under `src/lab-guide/` are read.

## Lab page anatomy (`LabGuide.tsx`)

A lab page has three stacked sections: **TheoryPanel** (collapsible, **default collapsed**) → **SimulationPanel** (collapsible, **default collapsed**, mounted once for the lab — visibility toggles, state preserved across phases; the student's open/closed choice is shared between the landing view and the guide via a single boolean) → **Laboratorieguide** (the gated 7-phase flow; the PhaseStepper is wrapped in a `sticky top-0` bar in `LabGuide.tsx` so phase progress stays visible while the student scrolls). Phase navigation uses URL hash; mode/labMode are query params.

### Phase box semantics — three text layers

Each phase has three distinct text surfaces, and only one of them owns the *task*: the **instruction-box** at the top (light-blue card, fed by `phase.steps` — see SPEC §8). Authoring `steps: string[]` makes `LabGuide.tsx` auto-render a `Fase N – {title}:` header above a `<ol type="lower-alpha">`; a single-item `steps` renders header + plain line (no letter). Use the legacy `intro: string` only for one sentence with no header — schema rejects both at once. The MDX **prose** around widgets is for motivation, scaffolding questions, or operational guidance — **never** restate a step there. **Widget labels** (the `prompt` prop on `<FreeTextResponse>`, `<Quiz>`, etc.) own the concrete input prompt.

A `locked` instruction-box tracker step carries an accessible `Tooltip` (`src/lab-guide/Tooltip.tsx` — a framework primitive, **not** an MDX widget: not in `widgets/`, not in `mdx.ts`) explaining why it is locked. The text comes from the step's optional `lockedHint` field, falling back to `strings.instructionBox.stepLockedHint`. The tooltip opens on hover, keyboard focus, and tap; dismisses on blur, Escape, or pointer-leave.

## State, persistence, gates

- Runner state (`src/lab-guide/runner.ts`) is persisted to `localStorage['htxlabs:state:${experimentId}']` on every change.
- On mount, `isStateCompatible` checks saved `experimentVersion` against current frontmatter; mismatch → silent wipe + restart (no banner; `console.info` only). Bump `frontmatter.version` whenever phase ids or gate structure change.
- Gates are pure (`gates.ts`) — discriminated union over `always | milestone | data-points | all-correct | all-checked | all-filled | keyword-count | predicate | rubric-required | all-satisfied | all-validated`. **Open-mode advances are unconditional** (`inquiryFreeAdvance`); guided/semi-guided run the actual gate. Add a new gate kind: extend the Zod `Gate` union in `src/lib/schema.ts`, then add one entry to `GATE_HANDLERS` in `gates.ts` (`{ check, message }`). `AUTHORABLE_GATE_KINDS` is derived from the handler map minus `SIM_DRIVEN_GATE_KINDS`, so a new widget-driven kind needs no further wiring; sim-driven kinds add themselves to the denylist.
- `rubric-required` (widget-driven) reads `{ kind: 'rubric', satisfied }` published by `<RubricResponse>`. The widget computes `satisfied` from the most recent rubric evaluation; editing the text flips a `dirty` derivation that recomputes `satisfied:false`, so the gate re-closes without the widget having to drop the prior result. Embed-server outage keeps the gate closed via the same derivation (literal/regex passes alone are not sufficient).
- `all-satisfied` (widget-driven, heterogeneous) ANDs the kind-aware satisfaction bit across a list of widget ids — `correct` from `'correct'`, `allChecked` from `'checked'`, `filled` from `'filled'`, `satisfied` from `'rubric'`, `foundCount === total` from `'keywords'`. Use it when a phase needs to gate on more than one widget type at once (e.g. a `VariableTable` + a `RubricResponse`); a single-widget case stays on the kind-specific gate. The schema enforces `widgetIds.min(2)` because a one-id `all-satisfied` would be a strictly weaker version of the kind-specific gate. Note: by default the `'filled'` projection is **presence-only** — adding `expected` to a `<VariableTable>` does NOT silently re-lock an `all-satisfied` gate. Correctness gating is explicit: either the kind-agnostic `all-validated` gate, or the **opt-in `strict: true` flag** on `all-satisfied`. With `strict: true`, the `'filled'` projection requires `filled && correct === true`; a widget without `correct` (no `expected` configured) fails strict — no silent degrade. Other kinds are unaffected by the flag. `<RevealWhen>` accepts the same `strict` prop, plus an opt-in `scrollOnReveal` that smooth-scrolls the revealed content into view and moves focus to it on the hidden→visible transition — transition-only (never on initial mount-while-visible), reload-safe via a registry-presence guard, and honoring `prefers-reduced-motion`. The projection helper `widgetSatisfied` is exported from `gates.ts` so both consumers share one source.
- `all-validated` (widget-driven, widget-agnostic) reads `correct: true` from any widget registering `kind: 'filled'` (currently `<VariableTable>` when its `expected` prop is set). Use this — not `all-filled` or `all-satisfied` — when a phase must require correct answers, not just presence. Single-widget gating is allowed (`widgetIds.min(1)`). The structured `errors` payload is opaque to gates.ts (`unknown`) — widget-specific shape lives in the widget's helper module. `<VariableTable>` publishes `correct: true` when every configured expected cell is **locked** (Tjek-confirmed + currently still correct via its matcher pairing); unlocking a cell (double-click / Enter or F2 / 500 ms long-press) immediately drops `correct` back to `false`.
- **Navigation is asymmetric by design**: forward advance is gate-checked, but completed/current phases are always reachable via the stepper (backward navigation is free). Don't symmetrize `canAdvanceTo` — `PhaseStepper.tsx` relies on the asymmetry to keep completed circles clickable.
- Widgets register live state (`registerWidgetState`) into a ref, not React state, so widget re-renders don't cascade through the runner. A `setTick` forces gate-evaluating subscribers to re-render after registration.
- A **parallel registry** — `registerWidgetCheck` / `widgetChecks` (`useRegisteredWidgetCheck` hook, `WidgetCheck` type) — lets a widget hand the `PhaseFooter` a callback so the footer's "Næste fase" button can drive the widget's Tjek (one footer button cycling check → check → advance). It is a per-widget-instance opt-in via the `checkInFooter` prop (currently `<VariableTable>` + `<RubricResponse>`; used by the template lab's phase 1). The check callback is kept out of `GateCtx` deliberately — pure gate evaluation must not see a React callback or live `disabled`/`pending` booleans. A check may also carry an optional `disabledReason` string; when set, the footer wraps the merged button in a hover `Tooltip` surfacing it (e.g. `<RubricResponse>`'s below-min-words hint — which therefore has no inline message) and renders the button `aria-disabled` rather than `disabled`, since a truly disabled `<button>` fires no pointer events and the tooltip would never open. Unlike registered widget *state* (which persists across phases), a check action **cleans up on unmount** — it must not outlive its widget.

## Widget conventions

- **Danish UI strings & author overrides** (SPEC §17): framework defaults live in `src/lab-guide/strings.da.ts` (templates use `{name}` placeholders, substitute via the exported `format()` helper). **Every student-facing string in a widget must follow the rule:** (a) the default lives in `strings.da.ts`, and (b) the widget accepts an override prop (`checkLabel`, `placeholder`, `tooShortMessage`, `correctMessage`, …). No hardcoded Danish in widget JSX. Pattern: `{prop ?? strings.widgets.<name>.<key>}`.
- **VariableTable per-section config**: `<VariableTable>` accepts an optional `iv` / `dv` / `constants` prop on each section, each shaped as `{ count: N }` (fixed row count, no +/× controls) or `{ min, max }` (student-pick within bounds). Defaults reproduce today's behaviour: IV/DV are single fixed rows, constants is `0..∞`. `expected.iv` and `expected.dv` accept either a single shorthand object (back-compat) or an array — both normalise to an array internally. The published `values` shape is uniformly `{ iv: VariableEntry[]; dv: VariableEntry[]; constants: VariableEntry[] }` regardless of count. Canonical authoring example: `testlabs/variable-table-test/flerdimensional`. PL14 guard: when an `expected.<section>` array exceeds a finite section `max`, the widget emits a dev-only warning and drops the extras.
- **VariableTable module layout**: `<VariableTable>` is split across flat siblings in
  `widgets/` — `VariableTable.tsx` (props + orchestrator + in-widget Tjek button),
  `VariableTableRows.tsx` (section + row), `VariableTableField.tsx` (one cell +
  `flashClasses`), and four pure logic modules: `variableTableValues.ts` (shared types,
  bounds, value rehydration), `variableTableLocks.ts` (lock resolution),
  `variableTableTjek.ts` (Tjek lock-diff + dim reason), `variableTableHints.ts` (hint
  ladders, spendable count, missing-row messages). `variableTableCorrectness.ts` remains
  the matcher. The shared types (`VariableEntry`, `VariableTableValues`, `SectionConfig`)
  live in `variableTableValues.ts` and are re-exported from `VariableTable.tsx`, which
  stays the widget's public entry point. `useVariableTableUnlockSession.ts` is the one
  hook inside `widgets/` — widget-specific, unlike the framework registries at
  `lab-guide/` root. Pure modules take component state as explicit parameters
  (`locks`, `errors`, `HintCtx`) rather than closing over it, which is what makes them
  directly unit-testable.
- **VariableTable lock model** (replaces the persistent emerald-ring "correct" cue): clicking Tjek is the event that commits per-cell correctness. Configured cells (those with `expected.<section>[i].<cell>` set) lock into a `readOnly` input styled as plain text when correct + filled, and flash `bg-emerald-100` for 1.5 s on the transition; wrong cells stay editable and flash `bg-rose-100`; empty cells are ignored. The published `correct` bit and the `sections.{iv,dv,constants}` facet both follow lock state — they flip to `false` the moment a student unlocks a cell. Unlock affordances are double-click (desktop), Enter or F2 on a focused locked cell (keyboard), and a 500 ms long-press (touch); focus moves to the freshly-rendered editable input on unlock. Locks are keyed by `${section}.${expectedIndex}.${cell}` (expected-row identity, the same scheme `variableTableHintTiers` uses), persisted under `RunnerState.variableTableLocks`. Author-overridable string: `lockedTooltip` (SPEC §17) — the leading `Korrekt.` doubles as the AT announcement.
- **Copy/paste protection** is opt-out, not opt-in. Use `ProtectedInput` / `ProtectedTextarea` for student free-text. The escape hatch is per-lab `frontmatter.allowPaste: true` (SEN accommodation) — `ExperimentRoute` injects it via `LabPasteContext`, and the protected primitives read the context as their default. Authors don't (and shouldn't) thread `allowPaste` through every widget; the widget-level `allowPaste` prop survives only as an explicit per-instance override and is normally absent.
- **Hint system** — `<RubricResponse>` and `<VariableTable expected>` participate in a request-driven, per-phase token bucket. Bucket UI (`HintBucket`) sits next to each Tjek (in-widget + footer); clicking it arms spend mode (`HintSpendContext`). The per-widget affordance differs by widget: **`<RubricResponse>`** uses the textarea itself as the spend target — armed = amber border + amber ring; click or Enter spends 1 token under **strict per-group gating**: the spend always targets the FIRST failing criterion in author order. If that criterion's ladder is capped and it remains failing, the spend is a no-op until the student satisfies it (edit + retjek). `registerSpendableCount` reports the active group's remaining tiers only — later criteria contribute 0 because they're unreachable in the strict model. The textarea has no focus-popup; instead a persistent feedback panel below the word counter shows a **flat hint list** with no criterion headers: pinned misconceptions at the top (orange flat-dash bullets, all triggered misconceptions across criteria), then the active group's spent-hint stack newest-on-top. When the active group's ladder is capped, the deepest hint carries the `➔` marker (text-accent, text-sm — the InstructionBox active-step glyph). The panel is sticky-after-first-show (one-way `widgetValues[${id}:panelShown]` bit) so it cannot vanish mid-edit while the student is reading and revising; it auto-hides when there's no failing-with-spent-hints criterion AND no pinned errors (so a fully satisfied widget doesn't leave an empty box behind). The bottom-left pip cluster (one pip per visible panel bullet) **doubles as the panel toggle**: clicking it collapses or reopens the panel; the collapse bit persists per-widget via `widgetValues[${id}:panelCollapsed]`. Any spend forces the panel back open. RubricResponse's pips are always-extended (no focus-within bridge animation — that pattern is VariableTable-only). **`<VariableTable>`** has no per-cell lightbulb — instead, every failing cell with a remaining ladder paints a faint amber border + becomes the spend target itself (click or Enter spends, exits spend mode, and re-focuses the cell so `HintPopup` opens against the freshly-revealed tier). Idle VT cells with popup content (paid reveals or live free diagnostics) carry a small persistent amber dot in the top-right corner so the student notices the popup is available before focus. The revealed tier text surfaces in the focus-triggered `HintPopup` beside the input (along with free misconceptions in orange and VT free `case-mismatch`/`whitespace-internal` diagnostics). VT's pip cluster keeps the focus-within bridge animation (idle short, grow on focus-within) — RubricResponse diverges by sitting symmetric around the textarea border at full size. Default pool is 3, replenish 2 min/token; both are author-overridable per phase via `hintPoolSize` / `hintReplenishMinutes` on the `Phase` schema (`0` disables hints or the timer respectively). Off-phase wall-clock time is discarded via `ANCHOR_HINT_TIMER` on phase entry — no grinding by parking on another phase. The 1 Hz countdown ticker + centralized `LAZY_REPLENISH` dispatcher live in `RunnerProvider` and are gated on the current phase having hint-eligible widgets (`registerHintEligibility` registry, populated by `useRegisteredHintEligibility` which reads `PhaseScopeContext`). **Author-edits to `hintPoolSize` are a version-bump-required schema change** — students would otherwise see a bucket smaller than the one their saved spend state was sized against.
